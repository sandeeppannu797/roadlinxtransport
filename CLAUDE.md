# Road Linx Transport

Brisbane freight company site. **The site's entire commercial value is organic
search rankings for local freight terms.** Titles, descriptions, canonicals, OG
tags and JSON-LD are production data, not copy to tidy up.

Status: the migration from the legacy static-PHP site
(`legacy-src/roadlinxtransport.com.au`) to the Next.js App Router is **complete**
— 50 public URLs, 54 prerendered routes, all verified against the legacy source.

## Commands

```bash
pnpm dev                # dev server
pnpm lint               # ESLint; legacy-src/ and content/ are ignored
pnpm build              # production build — also the only type-check
pnpm extract            # regenerate content/*.ts from legacy-src
pnpm verify [baseUrl]   # parity check, default http://localhost:3000
```

There is no unit test suite. `pnpm verify` is the test, and it always walks all
50 URLs; there is no per-URL filter.

**Run this after any change:**

```bash
pnpm build && pnpm start    # then in another shell:
pnpm verify
```

`scripts/verify-parity.mjs` walks all 50 inventory URLs and fails if a `.php`
path stops returning 301, if a canonical stops pointing at its own page, or if
a page's title, description, keywords, robots, canonical, OG/Twitter tags, H1,
JSON-LD blocks or set of internal links drifts from the legacy source. Expected
values are read from the PHP files rather than from `content/`, so it exercises
the whole pipeline. This is the safety net for this repo: don't skip it, and
don't weaken a check to make a change pass.

**`extract` and `verify` need `legacy-src/` in the repo root.** It is gitignored
and has never been committed, so a fresh clone does not have it and both
scripts die with ENOENT. Copy or symlink it in from an existing working copy.
Both resolve it relative to the working directory, so run them from the root.

## How content works

`content/*.ts` is GENERATED by `scripts/extract-content.mjs` from the legacy
PHP — hand edits are overwritten. To change page copy: edit `legacy-src`, run
`pnpm extract`, then `pnpm verify`.

- `content/locations.ts` / `services.ts` / `blog.ts` — the 40 landing pages
  (15 / 15 / 10), each a record of slug, head values, hero, prose, FAQs and
  related-service cards. All 40 render through `components/LandingTemplate.tsx`
  (the blog variant drops the quote sidebar); the `[slug]` routes set
  `dynamicParams = false`, so an unknown slug 404s.
- `content/pages.ts` — home, about, fleet, industries, privacy-compliance,
  quote, contact and the three hub indexes. `components/StaticPage.tsx` renders
  their `<main>` HTML whole.
- Prose and FAQ answers are raw HTML rendered with `dangerouslySetInnerHTML`.
  That is deliberate: it guarantees copy is _copied_, never paraphrased.
- Extraction fails if a page's visible FAQ text and its FAQPage JSON-LD
  disagree, so those 40 duplicated FAQ sets cannot silently drift apart.
- Every page's head tags go through `pageMetadata()` in `lib/meta.ts`. Next
  replaces rather than merges `openGraph`/`twitter`/`robots` per page, so it
  repeats the site-wide defaults from `app/layout.tsx`. Changing a default in
  the layout alone does not reach the pages.

### What is hand-ported rather than generated

Some markup comes from the legacy source but was ported to JSX by hand, so
`pnpm extract` does not update it. `pnpm verify` still checks it against legacy.

- **`/quote` and `/contact` bodies.** Only their `head` is read from
  `content/pages.ts`. The page body is JSX in `app/quote/page.tsx` and
  `app/contact/page.tsx`, and their extracted `mainHtml` is unused. Editing the
  body of `quote.php`/`contact.php` and re-extracting changes nothing. Their H1
  is still verified.
- **`components/Header.tsx` and `Footer.tsx`.** `pnpm verify` compares each
  page's set of internal links with legacy `header.php`/`footer.php`. A nav or
  footer link change must therefore be made in both places. There is no
  divergence mechanism for links: `EXPECTED_DIVERGENCES` only covers head tags.

### Adding a page

The slug lists are hardcoded in `scripts/extract-content.mjs` (`locationSlugs`,
`serviceSlugs`, `blogSlugs`, `staticPages`). A new landing page needs its PHP
file in `legacy-src`, its slug in that list and its path in
`legacy-src/url-inventory.txt`. Routes and the sitemap then pick it up from
`content/`. A new static page also needs its own `app/` route and an entry in
the explicit list in `app/sitemap.ts`.

## Deliberate divergences

`lib/corrections.ts` is the only place the site may differ from legacy, and
every entry needs a stated reason. `verify-parity.mjs` declares the same
expectations independently, so a wrong correction fails the check instead of
passing silently. One entry today: `/privacy-compliance` had its canonical and
og:url pointing at `/policies-compliance`, a URL that has never existed.

## Facts worth not rediscovering

- **`url-inventory.txt` is at `legacy-src/url-inventory.txt`**, not the repo root.
- **The two sidebar partials do NOT define internal linking.**
  `location-side-bar.php` and `service-side-bar.php` are identical quote-CTA
  cards differing only in overline text — "Local freight" vs "Get moving" —
  with no cross-page links. The real link structure is the header dropdowns,
  footer columns and each page's "You might also need" cards; `pnpm verify`
  checks it page by page.
- **`services/local-transport` is orphaned on purpose**: zero inbound links,
  `noindex, nofollow`, excluded from the sitemap. It is in the inventory, so it
  must still resolve. The nav's "View all 14 services" refers to the other 14.
- **Ignore these under `legacy-src/roadlinxtransport.com.au/`**:
  `roadlinxtransport(old-web)/` (an old WordPress copy), `wp-content/`,
  `PHPMailer/`, `Canvas.dc.php`, `support.js`, and the `.zip` files. None are in
  the inventory. Point ESLint away from `legacy-src` — it is already ignored.
- `legacy-src` is ~380MB. `.vercelignore` keeps it out of deploys, and nothing
  at build time reads it.
- Redirects use `statusCode: 301`, not `permanent: true` (which emits 308).
- Styling is the ported legacy CSS in `app/styles/` (design-system tokens plus
  `roadlinx.css`). Tailwind is installed but unused for site styling — do not
  reintroduce its preflight, it fights the legacy design.
- Legacy `site.js` behaviours are React now: `components/Header.tsx` (scroll
  state, active nav, mobile drawer), `SiteBehaviors.tsx` (FAQ accordion via
  delegation so it reaches inside HTML blobs, reveal-on-scroll),
  `FooterYear.tsx`.
- The home page's canonical ends in a slash, which Next's metadata layer would
  strip; `components/LiteralUrlTags.tsx` emits those two tags literally instead.
- `ORG_JSONLD` in `lib/site.ts` is byte-for-byte from legacy `head.php` and is
  on every page; verify compares it too.
- Forms are server actions plus Nodemailer (`app/quote`, `app/contact`), sending
  to the same addresses and body layout as the legacy `mail()` calls. SMTP creds
  come from env — see `.env.example`. Without them the forms show the legacy
  "Sorry, something went wrong" message and log the failure.
- `/sitemap.xml` and `/robots.txt` are generated from the content collections
  and filter out `noindex` pages (49 of 50 URLs). The legacy site had neither.

## Use your judgement freely on

Component structure, accessibility, responsive design, performance, images,
type safety, visual design.

Known deferred follow-up: `<img>` rather than `next/image`, left for a later
pass on purpose. The 5 lint warnings come from the quote/contact hero images
and the header/footer logos. The 40 landing-page hero images sit inside the
extracted `hero.media.html` strings, so lint never sees them, and moving them
to `next/image` means changing the extraction.
